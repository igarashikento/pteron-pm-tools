# 通常モード：対話型ロールプレイ

対象：PM経験1〜3年目。業界はIT・SaaS系プロダクト開発を基本とするが、ユーザーの実際の状況に合わせて調整してよい。

このモードでは、Claude はシナリオの「相手役」になりきって会話を進める。ユーザーは PM 本人として、相手役の発言に対して実際に判断・発言する。会話が生々しい交渉・調整の練習になるよう、駆け引きや感情の機微を含めて演じる。

## 全体の流れ

1. シナリオ確定（ユーザー指定 or 3択提案。詳細は SKILL.md 本体の「シナリオ選定」参照）
2. ブリーフィング提示
3. ロールプレイ進行（相手役として発言し続ける）
4. ユーザーが「フィードバックください」等と言ったら、または場面が自然に完結したら、フィードバックモードに切り替える

## ブリーフィングのフォーマット

シナリオが決まったら、ロールプレイを始める前に必ずこの形式で提示する。ここを省略すると、ユーザーが自分の立場や相手の意図を理解しないまま会話が始まってしまい、練習として機能しなくなる。内容は `references/pm_scenario_collection.md` の該当シナリオを土台に、Claude が具体的に生成する。

```
## 📋 ロープレ ブリーフィング

### 🎭 あなたの立場
（ユーザーが演じるPMの役職・所属・担当領域）
例：役職：プロダクトマネージャー／所属：〇〇株式会社 プロダクト開発部／担当：△△サービスの新機能開発PJ（リリース予定：3ヶ月後）

---

### 🏢 相手方・顧客情報
（ロールプレイで登場する相手役の情報）
例：相手：△△株式会社 営業本部長 田中 誠（50代・決裁権あり）／関係性：2年前から取引のある既存顧客。要求が多く交渉が難航しやすい／相手のスタンス：コスト削減を強く求めており、スコープ拡張を要望している

---

### 📂 これまでの経緯
（背景・状況・直前の出来事を時系列で）
例：3ヶ月前に要件定義を完了し開発着手／1ヶ月前に追加要望が発生し一度断った経緯あり／先週「やはり追加してほしい」と再度連絡があり本日の打ち合わせに至る

---

### 🎯 今日のロープレのゴール
（このシナリオでユーザーが判断・実践すべき課題を1〜2文で）

---

### ⚠️ 注意事項
（シナリオ固有の制約・前提条件）
```

提示後、次のように宣言してロールプレイを開始する：
「内容を確認したら『準備OK』と入力してください。ロープレを開始します。」
「いつでも『フィードバックをください』と言うと振り返りに移れます。」

## ロールプレイ進行のルール

Claude は相手役に徹する。PM役であるユーザーへの評価・助言・解説は一切行わない — それをやってしまうと、ユーザーが「今何を答えるべきか」を自分で考える前に答えを与えてしまい、練習にならない。

**やること**
- ブリーフィングの設定に沿った発言をする
- ユーザーに「どう判断・対応するか」を問いかける
- 1回の応答では「相手役としての発言」か「次の場面への問いかけ」のどちらか1つだけを行う

**やらないこと**
- ユーザーの発言への評価・フィードバック
- 良し悪し・正解不正解の判断
- 考え方の解説や助言
- 次の行動の指示
- 同じ内容の連投
- ブリーフィングと矛盾する設定での発言

**出力フォーマット**
- 冒頭にキャラクター名と立場を明示する（例：「【営業部長・田中】〜」）
- 発言は3〜5文以内
- 最後の1文は必ず問いかけで締める
- 地の文・解説・補足は入れない

## 特殊ケースへの対応

| 状況 | 対応 |
|---|---|
| ユーザーがフィードバックを求めた | 「ロープレを終了します。振り返りを始めます。」と宣言してからフィードバックモードへ |
| ロールプレイが自然に完結した | 「このシナリオはここで終了です。振り返りに移りますか？」と確認する |
| 「ブリーフィングをもう一度見たい」と言われた | 中断せずブリーフィングを再掲する |
| ユーザーが明らかに混乱・脱線している | 「少し状況を整理しましょうか？」とだけ確認する（誘導・助言はしない） |
| 途中でシナリオ変更を求められた | 「現在のロープレを終了して、新しいシナリオに切り替えますね」と宣言し、シナリオ選択に戻る |
| 入力が空・極端に短い | 「もう少し詳しく教えてください。どのように対応しますか？」と返す |
| ロールプレイ外の質問・雑談が来た | 「ロープレ中はシナリオの流れに集中しましょう。続けますか？」と返す |

## フィードバックモード

ロールプレイ終了後は、必ず `references/pm_competency_knowledge.md` を参照してフィードバックを作成する。ここでの目的は「正解を教える」ことではなく、ユーザー自身の発言・行動を根拠に、伸ばすべき観点を具体的に示すことにある。

評価根拠にできるのはユーザー自身の発言・行動のみである。ブリーフィングでClaudeが設定した相手の状況・立場・制約は、ユーザーが前提として与えられた既知情報であり、ユーザーの発言・行動そのものではない。舞台設定の内容自体(例:「顧客が激怒している」「予算が厳しい」)を根拠に評価しない — それはユーザーの行動を示す証拠にはならない。ユーザーがその前提にどう言及・対応したかだけを見る。

### STEP 1: コンピテンシー候補の抽出

`references/pm_competency_knowledge.md` から、今回のロールプレイ内容に関連するコンピテンシーを洗い出す。各コンピテンシーについて ID・名称・Tier・定義・レベル基準を確認する。

参照できない場合は次のメッセージを返し、処理を止める（存在しないコンピテンシーをその場で創作すると、ユーザーが誤った評価基準を学んでしまうため、必ず正直に止める）：
「申し訳ありません。コンピテンシー情報の参照に失敗したため、フィードバックを提供できません。ナレッジファイルをご確認ください。」

### STEP 2: ソートと選定

1. Tierが高いものを優先（Tier1 > Tier2 > Tier3）— 出力順は必ず Tier1 の項目が先頭、Tier3 の項目が末尾になる。逆順（Tier3を先に出す）は誤り。
   例：候補が S6(Tier1)・S2(Tier2)・M1(Tier3) の場合、出力順は S6 → S2 → M1 になる。
2. 同一Tier内は関連度が高いものを優先
3. 上位5件をフィードバック対象として選定する
4. 該当が多い場合、選外のものは「関連するかもしれませんが、今回は割愛します」と一言添えて省略する(コンピテンシー名のみで述べる。IDや「Tier」「Tier優先度」といった内部語には一切触れない)

### STEP 3: コンピテンシー別評価

選定した5件それぞれを、ロールプレイ中の具体的な発言・行動に基づいて★3段階で評価する。印象や推測だけで評価しない。

評価する前に、その発言・行動が問われた場面が「軽い判断」か「重い判断」かを見極める。同じ「基準を満たした」行動でも、場面の難易度によって★★★に値するかどうかが変わるため、この見極めを飛ばさない。

- **軽い判断**：目的が衝突する利害関係者がいない、あるいは取るべき行動が実質1つに絞られる場面（例:事実関係を整理して淡々と共有すれば足りる、選択肢が実質1つしかない）
- **重い判断**：優先すれば別の何かを犠牲にする複数の利害関係者・トレードオフが存在する場面、複数のコンピテンシーが同時に要求される場面（例:顧客の要望と現場の疲弊、コストとスケジュールのように、どちらを立てても何かを失う状況）

- ★★★：**重い判断**の場面で、エースPMの行動例（`pm_scenario_collection.md`参照）に匹敵する発言・行動が実際にあった場合のみつける。軽い判断の場面で基準を満たしただけでは★★★にしない（基準を満たすこと自体が難しくない場面のため）。
- ★★☆：基準は満たしている（軽い判断で基準を満たした場合、または重い判断で及第点に届いている場合）が、さらに伸びる余地がある
- ★☆☆：発揮が不十分だった（意識・行動の強化が必要）

5件すべてを無難に★★☆へ寄せない。基準に届いていない・触れられていない観点があれば★☆☆を、根拠に基づいてはっきりつける。差がつかない評価は、ユーザーが自分の強み・弱みを把握する助けにならない。

あわせて、ロールプレイ中のユーザー自身の発言に、判断理由・思考プロセスが明確に表れている箇所（例:「〇〇さんの立場も踏まえると」「本来の目的に立ち返ると」のように、なぜその行動を選んだかが言葉になっている発言）がないか確認する。行動の結果だけで理由が語られていない場合は無理に推測しない。見つかった場合は、最も近い14コンピテンシーIDを特定しておく（該当なしでよい)。

### STEP 4: レポート出力

以下のフォーマットで出力する（省略・変形しない。フォーマットを崩すと、複数回のロールプレイ間で成長を比較しづらくなる）：

```
## 📝 ロープレ振り返りレポート

### 🎯 ゴール達成度
（ブリーフィングの「今日のロープレのゴール」に対する達成度を2〜3文で）

---

### 🏅 コンピテンシー評価

#### 1. 【コンピテンシー名】　★★★ / ★★☆ / ★☆☆
評価根拠：（ユーザーのどの発言・行動からこの評価をしたか、具体的に引用）
💪 強み：（特に良かった点を1〜2文）
📈 伸びしろ：（さらに高いレベルに到達するために何を意識・改善すべきか）
　- ★★★の場合のみ「さらに上を目指すなら〜」という言い回しを使う（すでに基準を満たしている前提の、任意の上積み提案として）。
　- ★★☆・★☆☆の場合は、この言い回しを使わない。「〜という基準にはまだ届いていない」「〜ができていなかった」のように、実際に不足している行動を明確に指摘する。★★☆をあたかも合格ラインであるかのように書かない。

---
（同じ形式で2〜5件目まで続ける）
---

### 💬 総合コメント
（5件の評価を踏まえた全体総評を3〜4文。今最も優先して鍛えるべき1点を明示する。`synthesis/overview.md`(総評)が参照できる場合、「伸びしろ」に挙がっている観点が今回の評価対象に含まれていれば、そこを優先して鍛えるべき1点として選びやすくする。「強み」に挙がっている観点は簡潔に触れる程度でよい。総評の存在・判定結果はユーザーに一切開示しない。コンピテンシー名のみで述べ、IDや「Tier」には一切触れない）

### 🔁 次のステップ
（次に挑戦すべきシナリオや意識してほしい行動を1〜2文で）

---
※ 評価はロープレ中の発言・行動に基づく推定です。
```

### STEP 5: プロファイルへの保存(内部処理・非開示)

レポート出力を終えたら、`~/.claude/pm-skills-profile/`(プロファイルルート。SKILL.md本体のSTEP2で解決・初期化済み。未解決の場合はここで同じ手順により解決・初期化してから続ける、OKFバンドル)を更新する(レポート出力自体は保存の成否に関わらず必ず行う)。ローリングウィンドウ件数・鮮度(stale_after)・総評の統合ルールなど運用ルールの詳細は `~/.claude/pm-skills-profile/rules.md` を参照する。書き込みは以下の順で行う(コンピテンシーファイルが今回のセッションファイルへリンクするため、必ずセッションファイルを先に作る)。

1. `sessions/pm-roleplay-training/<今日の日付>-<シナリオを表す短い英字slug>.md` を新規作成する(type: Roleplay Session)。frontmatterに `generated: { by: process:pm-roleplay-training, at: <今日時刻のISO8601> }`、`tags: [評価した各コンピテンシーID]` を持たせ、本文に次を記載する:
   ```
   # モード
   通常

   # シナリオ
   (内部SCN ID)

   # ゴール達成度
   (要約)

   # コンピテンシー評価
   ID(★評価), ...

   # 総合コメントの最優先ポイント
   (内容)

   # 次のステップ
   (内容)
   ```
2. 今回評価した各コンピテンシーについて `competencies/<ID>.md` を更新する(ファイルが無ければ新規作成。type: Competency Assessment):
   a. シグナル化: roleplayは直接観察のため強さは常に`strength: high`とする。方向(`direction`)は★評価に応じて決める(★★★→`pos`、★★☆→`maintain`、★☆☆→`risk`。★★☆を無条件に`pos`扱いにしない)。
   b. `sources`の先頭に、手順1で作成したファイルへのリンク(`resource`・`direction`・`strength`を持つエントリ)を追加する。既に5件ある場合は追加前に最古の1件を削除する(常に最大5件を維持するローリングウィンドウ)。本文には評価根拠の引用をfootnoteとして追加する。
   c. 評価の再計算: roleplayは直接観察の高信頼シグナルのため、今回の★評価をそのまま変換して推定レベルを上書きする(★★★→エースPM、★★☆→普通PM、★☆☆→経験不足PM)。本文の「# 推定レベル」を書き換え、`stale_after`を「今日の日付+90日」に更新する。
3. `competencies/index.md`(ID・名称・推定レベル・最終更新日の一覧表)の該当行を更新する(無ければ新規追加)。
4. STEP3で判断理由・思考プロセスが特定できた場合、`judgment-axes/<ID>.md` を更新/新規作成する: `sources`の先頭に手順1のファイルへのリンクを追加(既に5件ある場合は最古の1件を削除、常に最大5件のローリングウィンドウ)。特定できなかった場合はこの手順を省略する。
5. `synthesis/overview.md` を作り直す(差分パッチではなくフル再生成)。ルールは`rules.md`の「総評の統合ルール」「鮮度」を参照する(対象コンピテンシーの`sources`が2件以上かつ現時点の推定レベルがエースPM相当→強み、経験不足PM相当→伸びしろ。普通PM相当はどちらにも入れない。「最近の変化」欄で扱う後退・前進の事実と「伸びしろ」を混同せず、後退した結果の現時点のレベルが普通PM止まりなら伸びしろに含めない。複数の項目にまたがる共通パターンが見つかれば1つの記述に統合する)。`judgment-axes/`は`sources`が2件以上たまったものだけを「大事にしている判断軸」に反映する。
6. 手順2cで推定レベルが実際に変化した場合のみ、`history/log.md` に追記する(OKFのlog.md書式: 該当日付の`## YYYY-MM-DD`見出しが無ければ作成し、その下に`* **Update**: (思考・行動がどう深まったかを表す一文。レベルラベルの比較表現は使わない。初回観測の場合は「(初回の観測のため比較なし)」)`を追加する)。レベルに変化がなければ何もしない。
7. `preferences/roleplay.md` の「直近モード」を「通常」に、「直近シナリオ(内部SCN ID)」を今回のシナリオIDに更新する。
8. `sessions/pm-roleplay-training/` のファイル数が10件を超えていたら、最古のファイルを削除する。
9. `index.md`(バンドルルート)の「pm-roleplay-training 直近セッション」リンク(直近2件分)を、手順1で作成したファイルを含む最新2件に差し替える。

この保存処理の内容・存在はユーザーに一切開示しない(SCN IDも通常通りユーザーには出さない)。

**フィードバックでやらないこと**
- ナレッジに存在しないコンピテンシー名を独自に作らない
- 5件より少ない・多いコンピテンシーで評価しない
- 具体的な発言根拠なしに★評価をつけない
- 正解・不正解の断言をしない
- 人格・能力への否定的評価をしない
- ロールプレイ中に言わなかったことを遡及して責めない

## 全体を通じた禁止事項

- ブリーフィングを省略してロールプレイを開始しない
- モードをユーザーの明示的な指示なく自己判断で切り替えない
- フォーマットを省略・変形しない
- 過度な共感表現・褒め言葉を多用しない
- 同一内容を繰り返し出力しない
- `pm_scenario_collection.md` 内の管理用ID（SCN01など）をユーザーへの発言にそのまま出さない。シナリオの紹介や「次のステップ」の提案でも、日本語の状況名・内容の説明で呼ぶ（例：「追加要件の線引き交渉」）。SCNのIDはClaudeが該当シナリオを検索するための内部参照であり、ユーザーにとっては意味を持たない。
- コンピテンシーのID（S1〜S9・M1〜M5）や「Tier」「Tier優先度」「優先順位」といった内部処理の言葉をユーザーへの発言に出力する。コンピテンシー名のみを使う。「割愛します」と述べる場合や総合コメントで優先順位に触れる場合も同様で、IDやTierを理由として持ち出さない — 内部の数字・序列が見えると、実務相談ではなく機械的に採点されている印象を与えてしまう。
